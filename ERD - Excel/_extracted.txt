R2: CMS Database — Stored Procedure Generation Handoff
R4: Purpose
R5: Read this first | This workbook is the complete schema specification for a CMS database. The receiving agent should produce SQL Server CREATE TABLE scripts and the full set of stored procedures listed in 'Required SPs'. Test all output against the scenarios in 'Test Scenarios'.
R6: Target dialect | Microsoft SQL Server 2019+. Use NVARCHAR for any string with international content; VARCHAR is acceptable elsewhere. DATETIME2 preferred over DATETIME where new.
R8: Sheet Index
R9: Handoff | This sheet — conventions, glossary, what to produce.
R10: ERD v2 | Authoritative schema. 20+ tables across lookups (blue), core entities (green), junctions (red), tags (purple). Change log in column R.
R11: Stored Procedures | Worked example of the Add-New-Client SP flow (usp_Client_Add orchestrator + 6 child SPs). Use as the style template for all other SPs.
R12: Required SPs | Definitive checklist of every stored procedure to produce, grouped by entity.
R13: Seed Data | Initial rows for lookup tables (tStatus, tStatusType, tStatusAppliesTo). Load these before testing.
R14: Delete Policy | Per-FK cascade rules + soft-delete implementation checklist. Pattern 4 (Hybrid).
R15: Test Scenarios | End-to-end test cases (happy path, edge cases, integrity checks) to validate the generated SPs.
R16: Sheet1 | ORIGINAL v1 schema for reference only. DO NOT use — superseded by ERD v2.
R17: T-SQL Templates | Reference implementations for each SP shape (lookup GetOrCreate, entity Add, partial Update, soft-delete, restore, junction add, history insert, paged list, activity log helper, status validator). Use as copy-paste templates.
R18: Conventions
R19: Symbol legend | 🔑 = Primary Key   🔗 = Foreign Key   ⭐ = UNIQUE constraint   🆕 = New in v2 (vs Sheet1)   🔄 = Renamed/Changed in v2
R20: Table naming | All tables prefixed with 't' (singular). Junctions also use 't' prefix (e.g. tUserGroupUser). Views prefixed 'v' (e.g. vClient).
R21: PK naming | Full entity name + ID (BusinessUnitID, ClientID, ProjectID). Exception: legacy abbreviations preserved where shown (UGID, etc.) — use what the ERD specifies, do not rename.
R22: SP naming | usp_<Entity>_<Action>. Examples: usp_Client_Add, usp_Client_Get, usp_Client_Update, usp_Client_SoftDelete, usp_Client_Restore, usp_Client_List, usp_Project_AddService, usp_Project_AddRevenue.
R23: Audit columns | Every transactional table has CreatedDate, ModifiedDate. SPs must set these (CreatedDate on Insert, ModifiedDate on Update). Use GETDATE() / SYSDATETIME().
R24: Soft-delete pattern | tClient, tProject, tUser, tUserGroup, tService have IsDeleted BIT + DeletedDate. Reads go through views (vClient etc.) that filter IsDeleted=0. SoftDelete SPs flip the flag; Restore SPs flip it back. Hard DELETE never occurs on these tables.
R25: Transactions | Every multi-statement SP must wrap work in BEGIN TRAN / COMMIT TRAN with TRY/CATCH and ROLLBACK on error. Return error info via THROW (not RAISERROR).
R26: Activity log | Every Insert/Update/SoftDelete/Restore must write a row to tActivityLog (EntityType, EntityID, UserID, Action, FieldName/OldValue/NewValue when applicable).
R27: Error handling | SPs validate inputs and THROW 50000+ custom errors on business rule violations (e.g. 'Project number already exists'). FK and UNIQUE violations from the DB are allowed to propagate.
R28: Parameters | Use @PascalCase parameter names matching column names. Nullable parameters default NULL. Output parameters for new IDs (@NewClientID INT OUTPUT).
R29: Indexes | In addition to PKs and FK indexes, the agent should propose indexes for: (a) filtered UNIQUE on natural keys where IsDeleted=0, (b) (EntityType, EntityID, ActionDate DESC) on tActivityLog, (c) composite covering indexes for any List SP with filtering.
R31: Deliverables
R32: 1. DDL | CREATE TABLE scripts for every table in ERD v2. Include PKs, FKs (with ON DELETE rules per Delete Policy sheet), CHECK constraints (e.g. tUser.UserType IN ('Internal','External') + the BU/Client XOR rule), filtered UNIQUE indexes, computed columns if useful.
R33: 2. Views | vClient, vProject, vUser, vUserGroup, vService — each SELECT * WHERE IsDeleted=0. Plus convenience views: vProject_Current (with latest Revenue), vClient_WithBU (with BU resolved through BusinessClass).
R34: 3. Stored procedures | Every SP listed in the 'Required SPs' sheet. Follow the conventions above and use the 'Stored Procedures' sheet's usp_Client_Add example as the style template.
R35: 4. Seed data | INSERT statements for tStatus, tStatusType, tStatusAppliesTo from the 'Seed Data' sheet. Plus a minimum set of tBusinessUnit, tClientCategory, tClientType, tProjectType, tUserRole rows so tests have data to work with.
R36: 5. Test harness | Optional but recommended: t-SQL scripts that execute each scenario in the 'Test Scenarios' sheet and assert expected outcomes.
R38: Open Decisions
R39: tUserRole tags | tUserRole has Tag1/Tag2/Tag3 columns — inconsistent with the tTag pattern used elsewhere (tServiceTag, tBusinessClassTag). Either keep as-is (user's explicit choice) or normalize to a tUserRoleTag junction. Default: keep as-is.
R40: Two UserRoleIDs | tUserGroup.UserRoleID (group's default role) and tUserGroupUser.UserRoleID (member-specific role). Application logic decides which wins when both are set; the DB does not enforce.
R41: BC → BU immutability | tBusinessClass.BusinessUnitID is the sole path from a Client to its BU. Consider whether changing this column after Clients are attached should be allowed (currently unrestricted). Recommend: enforce in SP layer (usp_BusinessClass_Update blocks change if any Clients reference it).

R6: 1 | usp_CreateTable_tBusinessUnit | CREATE OR ALTER PROCEDURE usp_CreateTable_tBusinessUnit
AS
BEGIN
    SET NOCOUNT ON;

    IF OBJECT_ID('dbo.tBusinessUnit', 'U') IS NULL
    BEGIN
        CREATE TABLE dbo.tBusinessUnit (
            BusinessUnitID INT IDENTITY(1,1) NOT NULL,
        BusinessUnitName             VARCHAR(100)         NOT NULL,
        BusinessUnitDescription      VARCHAR(255)         NULL,
        IsActive                     BIT                  NOT NULL CONSTRAINT DF_tBusinessUnit_IsActive DEFAULT (1),
        CONSTRAINT PK_tBusinessUnit PRIMARY KEY CLUSTERED (BusinessUnitID),
        CONSTRAINT UQ_tBusinessUnit_BusinessUnitName UNIQUE (BusinessUnitName)
        );
    END;

    -- Seed rows (idempotent)
    SET IDENTITY_INSERT dbo.tBusinessUnit ON;

    MERGE dbo.tBusinessUnit AS tgt
    USING (VALUES
        (1, 'US', 'U.S. Clients',          1),
        (2, 'UK', 'U.K. Clients',          1),
        (3, 'LA', 'Latin America Clients', 1),
        (4, 'Global', 'Global Clients',    1)
    ) AS src (BusinessUnitID, BusinessUnitName, BusinessUnitDescription, IsActive)
      ON tgt.BusinessUnitID = src.BusinessUnitID
    WHEN NOT MATCHED BY TARGET THEN
        INSERT (BusinessUnitID, BusinessUnitName, BusinessUnitDescription, IsActive)
        VALUES (src.BusinessUnitID, src.BusinessUnitName, src.BusinessUnitDescription, src.IsActive);

    SET IDENTITY_INSERT dbo.tBusinessUnit OFF;
END;

      ON tgt.ProjectTypeID = src.ProjectTypeID
    WHEN NOT MATCHED BY TARGET THEN
        INSERT (ProjectTypeID, ProjectTypeCode, ProjectTypeDescription, IsActive)
        VALUES (src.ProjectTypeID, src.ProjectTypeCode, src.ProjectTypeDescription, src.IsActive);

    SET IDENTITY_INSERT dbo.tProjectType OFF;

SHEET: Delete Policy
================================================================================
R2: Delete Policy — Pattern 4 (Hybrid)
R4: Tier | Tables | Strategy | Notes
R5: Lookups | tBusinessUnit, tBusinessClass, tClientCategory, tClientType, tProjectType, tServiceCategory, tUserRole, tStatusType, tTag | Block (NO ACTION) | Use IsActive=0 to retire. Never physically delete — breaks historical FKs.
R6: Business entities | tClient, tProject, tUser, tUserGroup, tService | Soft delete | IsDeleted=1 + DeletedDate stamped. Filtered views (vClient, vProject, etc.) hide deleted rows. UNIQUE constraints on natural keys (Email, ProjectNumber, UserGroupNumber) need to be filtered: WHERE IsDeleted=0.
R7: Owned children | tUserAddress, tProjectService, tUserGroupUser, tServiceTag, tBusinessClassTag, tStatusAppliesTo, tProjectRevenue, tProjectNote | CASCADE | ON DELETE CASCADE on FK to parent. Lifecycle is bound to parent — no independent meaning. When parent is soft-deleted, children stay (only parent's IsDeleted flips); when parent is hard-deleted, children go with it.
R8: Status / classification | tStatus | Block (NO ACTION) | Use IsActive=0. Status rows referenced by many business entities — deletion would orphan them.

R43: 2 | Filtered UNIQUE indexes on natural keys: CREATE UNIQUE INDEX UQ_tClient_Email ON tClient(Email) WHERE IsDeleted = 0;
